# Architecture

This document describes the intended structure and dependency boundaries of the service.

Keep this document synchronized with meaningful architectural changes.

The architecture should remain as small as possible while preserving clear responsibilities.

---

## Design Goals

The codebase should optimize for:

1. correctness;
2. readability;
3. clear public contracts;
4. testability;
5. simple dependency direction;
6. easy contribution by another developer.

Avoid architecture whose complexity exceeds the problem it solves.

---

## System Boundary

At a high level:

```text
Caller
  ↓
FastAPI HTTP API
  ↓
Application / domain behavior
  ↓
Provider boundary
  ↓
Provider-specific implementation
  ↓
External provider
```

Responses travel back through the same layers:

```text
External provider
  ↓
Provider-specific translation
  ↓
Domain representation
  ↓
FastAPI response
  ↓
Caller
```

Provider SDK objects should not become public API objects.

---

## Responsibilities

### HTTP Layer

Responsible for:

- HTTP request parsing;
- path/query/body validation;
- invoking application behavior;
- HTTP response serialization;
- HTTP status codes.

Should remain thin.

Should not contain substantial provider-specific logic.

---

### Application / Domain Layer

Responsible for:

- service-level behavior;
- domain decisions;
- coordinating operations;
- working with provider-independent domain data where applicable.

Application logic should not depend unnecessarily on HTTP concepts.

---

### Models

Responsible for:

- explicit data shapes;
- public request and response models;
- important domain invariants.

Use Pydantic at API/configuration boundaries.

Use simpler Python types or dataclasses internally when they communicate the model more clearly.

---

### Provider Integration

Responsible for:

- provider authentication;
- provider SDK/API calls;
- provider-specific identifiers where necessary;
- translating provider-specific representations into service-domain representations;
- translating provider failures at the appropriate boundary.

Provider SDK-specific types should remain localized here.

---

### Configuration

Responsible for:

- environment-based configuration;
- provider configuration;
- credential locations or references.

Secrets must never be hardcoded or committed.

---

## Dependency Direction

Prefer dependencies that point inward toward service/domain concepts.

Conceptually:

```text
HTTP
 ↓
Application
 ↓
Domain contract
 ↑
Provider implementation
```

External provider details should not spread throughout the application.

Avoid circular dependencies.

---

## Code Organization

Do not create directories merely to satisfy this diagram.

Create modules when actual behavior justifies them.

A possible structure is:

```text
app/
├── main.py
├── models/
├── routes/
├── services/
└── providers/
```

The exact structure may evolve.

Prefer a few coherent files over many trivial modules.

---

## Request Flow

For every public operation, a contributor should be able to trace:

```text
HTTP input
    ↓
validation/parsing
    ↓
application decision
    ↓
provider interaction, if required
    ↓
provider → domain translation
    ↓
public response construction
```

Document unusual deviations.

---

## External Boundaries

External dependencies should have clear boundaries because they are:

- slower than local code;
- capable of failing independently;
- difficult to reproduce deterministically;
- often provider-specific.

Tests should normally control these boundaries using fakes, fixtures, or mocks.

Real-provider verification is separate.

## Provider Boundary

The service uses this provider-independent contract for calendar operations:

```python
class EventProvider(Protocol):
    def get_event(self, event_id: str) -> Event: ...
    def list_events(self, limit: int) -> list[Event]: ...
    def create_event(self, event: CreateEventRequest) -> Event: ...
    def replace_event(self, event_id: str, replacement: EventReplacement) -> Event: ...
    def patch_event(self, event_id: str, changes: EventPatch) -> Event: ...
    def delete_event(self, event_id: str) -> None: ...
```

`get_event` retrieves one event by its service-visible identifier. The
`event_id` input is an opaque string supplied by the caller, and the return
value is the existing service-domain `Event` model. The operation is read-only:
it does not create, update, or delete provider state. Callers may depend on
these properties, but not on Google identifiers, request shapes, response
objects, or SDK types.

`create_event` accepts only the provider-independent title and timed-event
boundaries. It returns the created domain `Event`, including the identifier
generated by the provider. Google request bodies and responses do not cross
this interface.

Normal execution follows this dependency direction:

```text
FastAPI route
    ↓
application event operation
    ↓
EventProvider
    ↓
GoogleCalendarProvider
    ↓
Google Calendar SDK/API
```

Tests replace the provider at the same boundary:

```text
test
    ↓
application event operation
    ↓
EventProvider
    ↓
ControlledEventProvider
```

Application code depends only on `EventProvider` and domain models, while HTTP
code remains provider-independent. Google SDK calls, request construction,
response parsing and translation, and Google-specific configuration remain
inside the concrete Google provider. Neither raw provider dictionaries nor
Google SDK objects cross the interface. Startup or other composition code
selects and supplies the concrete provider; application logic must not import or
construct it.

Issue #51 explicitly extends the original Levels 3–4 interface with
the listing and creation operations; the GET-one signature is unchanged.
Listing accepts a validated limit from 1 to 100, returns a possibly short or empty
list in provider order, and changes no calendar state. Creation accepts only
provider-independent event values and returns the created domain `Event`. All
operations use the same composition boundary and service errors. This interface
contains only operations required by the public API and does not imply multiple
real providers or runtime provider switching.

## Architectural Changes

### Final operation 6: deletion

Issue #51 adds `delete_event(event_id: str) -> None` to `EventProvider`.
The HTTP validation dependency checks the opaque ID before client construction.
The application repeats that validation for non-HTTP callers and invokes the
injected provider once. The Google adapter calls `events.delete` on the configured
calendar and translates failures; no SDK response crosses the boundary.

HTTP returns an empty 204 only after deletion succeeds. Existing exception
handlers render failures and log `operation=delete_event`, category, status, and
provider involvement without IDs, credentials, or raw errors. Request-scoped
client cleanup is reused on success and failure. There is no retry or rollback
promise: a lost response can leave the event deleted despite a 502.

Live deletion verification showed that Google GET can still return the deleted
event's old fields with `status=cancelled`. The retrieval adapter treats this
tombstone as `NotFoundError` before translating its fields, so deleted events
cannot reappear as successful public reads. Active-event retrieval is unchanged.

### Final operation 4: complete replacement

Issue #51 extends `EventProvider` with the single operation required by PUT:
`replace_event(event_id: str, replacement: EventReplacement) -> Event`.
`EventReplacement` contains validated `title`, `start`, and `end` strings; it is
immutable and does not change the existing `Event` response model. The provider
replaces external state and returns the resulting domain Event. Shared service
errors describe missing resources, permission denial, and provider failures;
failed writes may have taken effect.

The PUT validation dependency checks the ID and complete body before resolving
`get_event_provider`. Malformed JSON uses the shared HTTP error renderer. The
application operation validates the ID again for non-HTTP callers and uses only
the protocol. Google request construction and translation stay in
`GoogleCalendarProvider.replace_event`. Composition, request-scoped client
ownership/cleanup, and existing GET behavior are unchanged. There is no cache on
this implementation branch. PUT failure logs use `operation=replace_event` with
the existing sanitized fields.

Before introducing a new:

- abstraction;
- service layer;
- factory;
- interface;
- dependency;
- queue;
- cache;
- database;
- worker;
- package;

answer:

1. What concrete problem does it solve?
2. Why is the current simpler structure insufficient?
3. What additional complexity does it introduce?
4. How will it be tested?
5. Can the same goal be achieved more simply?

Do not add architectural machinery based only on anticipated future needs.

## Level 5 HTTP Failure Boundary

FastAPI registers handlers for the four service exceptions from `app.errors`.
`app/http_errors.py` maps them to the exact public responses in
[CONTRACT.md](CONTRACT.md); it neither inspects Google exceptions nor returns
exception text. Other exceptions remain distinguishable from expected failures.

Routes run applicable application validation before resolving the provider
dependency. Retrieval rejects blank IDs without changing other identifiers.
Creation rejects invalid request bodies, blank titles, timestamps without UTC
offsets, and end times that are not after their start before a provider write.

Failure logs contain operation, service error code, HTTP status, and request-local
`provider_involved` context. This flag means provider setup or retrieval was
attempted, not that a remote call completed. It is false for locally rejected
input and true when composition or retrieval begins; unavailable context is
recorded as unknown. Logs exclude exception text, request headers, event IDs,
provider payloads, and expected-failure tracebacks.

The Google client remains request-scoped and is closed in the composition
dependency's `finally`, including when an operation raises a handled service error.

## Bounded Event Listing (#51)

The list route validates its limit before provider resolution, using the same
integer parser as FastAPI and the shared application bounds. Non-HTTP listing
also checks the bounds. The existing error handler uses request-local operation
context for listing logs and its fixed `Invalid event limit` message; GET-one
messages and the shared error structure remain unchanged.

`GoogleCalendarProvider.list_events` performs one `events.list` call, expands
recurrences, and translates at most `limit` items into domain Events. Google
failure classification is reused; unsupported event shapes become
`ProviderFailureError`. No public pagination or listing cache is introduced.

For G provider records fetched and N = min(G, limit) returned, the SDK holds the
raw page and translation builds N domain objects. Local work and memory are
O(G + N) for fixed-size records (actual payload bytes also matter), with exactly
one provider request and no traversal of later pages. Google normally returns
G <= limit and may return fewer. Its internal query cost is unknown.

## Event Creation Flow

`POST /events` parses a `CreateEventRequest` and validates its title and
timestamp ordering before provider resolution. Application logic calls only
`EventProvider.create_event`. `GoogleCalendarProvider` constructs the Google
`events.insert` body, executes the provider write, translates the returned
Google event into `Event`, and maps Google failures to the shared service
errors. The request-scoped client is closed on success and failure.

### Final operation 5: partial update

Yasmin's PATCH operation adds
`patch_event(event_id: str, changes: EventPatch) -> Event` to `EventProvider`.
`EventPatch` records the supplied subset of editable string fields. The HTTP
validation dependency rejects invalid bodies/IDs before provider setup; application
validation also protects direct calls. One changed time boundary requires a domain
`get_event` read before interval validation. The adapter maps only supplied fields
to Google's patch body and returns the translated Event. Existing service errors,
request-scoped client cleanup, and failure logging are reused. No cache exists in
this branch, and no cache infrastructure was added.
